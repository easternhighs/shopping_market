# 构建文档：Go 仿真网购平台（秒杀高并发）

本文件是项目的唯一构建依据。任何开发、搭建、改动前先读这里。配套进度记录见 `docs/progress.md`。

本文默认读者是完全不了解的新手，尽量用直白的话说明；不会默认你已经懂后端、数据库、消息队列等概念。

## 0. 这个项目是什么

一句话：用 Go 写一个“假”的网购网站，重点演示高并发下的“秒杀”场景怎么扛住流量、不超卖、不出错。

“假”指的是：支付、物流、短信、第三方登录都不接真实服务，用模拟接口代替；但用户、商品、购物车、下单、库存、订单、秒杀这些核心业务要真实可运行。

## 1. 项目目标

- 定位：面试项目，重点展示高并发处理能力和优化思路。
- 核心亮点：秒杀。
- 目标峰值：约 1 万 QPS（每秒 1 万个请求）。
- 当前架构：模块化单体；未来可按需拆成微服务。
- 数据库：MySQL；缓存：Redis；消息队列：Kafka。
- 秒杀使用独立页面，不复用普通商品下单页。

## 2. 技术选型（新手版解释）

- Go：写后端服务的主语言，天生适合处理大量并发请求。
- Gin：处理 HTTP 请求的 Web 框架，帮助我们写接口。
- MySQL：保存用户、商品、订单等需要长期存放的数据。
- Redis：内存缓存，速度极快；秒杀时先在这里“占坑”扣库存，挡住大量请求。
- Kafka：消息队列，像排队窗口；把瞬间涌入的请求先排队，后端再慢慢处理。
- Docker Compose：一条命令启动 MySQL、Redis、Kafka 等环境。

## 3. 整体思路：模块化单体

- 一个程序里按业务分模块：`user`（用户）、`product`（商品）、`cart`（购物车）、`order`（订单）、`inventory`（库存）、`seckill`（秒杀）、`payment`（支付）、`message`（消息）。
- 模块之间通过“函数/接口”调用，不直接操作别的模块的数据表，也不做跨模块联表查询。
- 将来拆微服务时，把这些模块分别变成独立服务即可，模块边界基本不变。

## 5. 两条核心链路

### 5.1 普通下单链路

用户登录 → 浏览商品 → 加入购物车 → 提交订单 → 扣库存 → 创建订单 → 模拟支付 → 订单状态流转。

这条链路先做，用来把“下单、库存、订单、支付”这些基本功跑通。

### 5.2 秒杀链路（核心亮点）

独立秒杀页 → 网关限流 → 应用层校验（时间、登录、限购）→ Redis 原子预扣 → Kafka 异步下单 → 消费端 MySQL 最终扣减与建单。

原则：**入口尽早拦截，核心写操作只有一次，MySQL 永远做最后防线。**

## 6. 数据表（概要）

- 用户表：登录账号、密码哈希、昵称。
- 商品表、SKU 表：商品信息和具体规格。
- 库存表：各 SKU/活动的库存数量。
- 购物车、购物车明细：临时存放“想买的东西”。
- 订单、订单明细：一次购买生成的订单和买了哪些商品。
- 支付流水：模拟支付记录。
- 秒杀活动、秒杀商品：什么时候抢、抢什么、有多少库存、每人限购几件。
- 秒杀订单、消息表：秒杀成功后的订单，以及待处理的异步消息。

具体字段在建表阶段逐个确定，每个阶段只建该阶段需要的表。

## 7. 分阶段构建计划

### 阶段 0：环境准备与项目骨架

- 目标：能跑起来一个返回 `ok` 的 Go HTTP 服务，并启动 MySQL、Redis、Kafka。
- 任务：
  - 初始化 Go 模块；
  - 建立目录结构；
  - 编写配置读取和程序入口；
  - 编写 `docker-compose.yml`；
  - 提供健康检查接口。
- 挖空点：配置读取、服务启动、健康检查接口。
- 完成标志：执行启动命令后访问健康检查接口返回成功；`docker ps` 能看到三个基础服务。

### 阶段 1：用户模块（注册/登录）

- 目标：能注册、能登录、登录后能识别“你是谁”。
- 任务：建用户表；实现注册、登录接口；密码加密；签发/校验登录令牌（JWT）。
- 挖空点：用户表建表语句、密码校验、登录令牌签发。
- 完成标志：能注册一个用户，能用该用户登录并访问一个“需要登录”的接口。

### 阶段 2：商品与库存模块

- 目标：能创建/查看商品，能表示商品有多少库存。
- 任务：建商品、SKU、库存表；实现商品增删查；实现库存查询和基础扣减。
- 挖空点：商品查询逻辑、库存扣减函数。
- 完成标志：能创建商品、查看商品，库存扣减后数字正确。

### 阶段 3：购物车与普通下单

- 目标：跑通“加购 → 下单 → 扣库存 → 生成订单 → 模拟支付”整条链路。
- 任务：购物车接口；下单接口；订单状态流转；模拟支付回调；下单幂等。
- 挖空点：下单事务、库存扣减与订单创建的配合、状态流转、幂等键。
- 完成标志：一个用户能完整买一次东西，库存和订单都正确，重复请求不会生成重复订单。

### 阶段 4：秒杀核心模块

- 目标：实现独立秒杀页，用 Redis + Kafka 把 MySQL 从瞬时高并发中隔离开，并保证不超卖。
- 任务：
  - 建秒杀活动、秒杀商品、秒杀订单表；
  - Redis Lua 原子预扣；
  - Kafka 生产与消费；
  - MySQL 条件更新做最终扣减；
  - 用户限购与防重复下单。
- 挖空点：Lua 脚本、Kafka 生产者/消费者、MySQL 条件更新、防重逻辑。
- 完成标志：模拟抢购结束后库存恰好为 0，不超卖，同一用户不会重复抢到。

### 阶段 5：高并发增强

- 目标：把 1 万 QPS 下可能出现的边界问题补齐。
- 任务：限流、防刷、缓存一致性、失败补偿、对账任务、日志/指标监控。
- 挖空点：限流器、对账任务、失败回补。
- 完成标志：压测时系统稳定，Redis/MySQL 数据最终一致，出现异常能告警或自动补偿。

### 阶段 6：压测与优化

本阶段分三条线，按优先级依次做。**6.1 是主线，6.2 和 6.3 都是为主线服务的**：
先把系统真正压到 1 万 QPS，再谈怎么把这件事演示出来、怎么让系统自己发现问题。

#### 6.1 冲 1 万 QPS（主线，已完成）

- 目标：把峰值 QPS 从约 5,900 提到约 1 万，并留下每一步的前后对比数据。
- 已知瓶颈：一次抢购要在 Redis 上做 4 次顺序往返（限流计数、读商品缓存、读活动缓存、Lua 预扣）。
  隔离基准测出：4 次往返上限约 9,000/s，**合并成 1 次往返后约 27,000/s**。
- 任务：
  - 把「限流 + 读商品信息 + 校验活动时间 + 防重 + 限购 + 预扣库存」合并进**同一个 Lua 脚本**，
    整个抢购在 Redis 上只花 1 次往返；
  - 缓存没准备好时回源 MySQL 填充后重试（冷路径，不影响热路径）；
  - 重跑全量回归：状态码、吞吐曲线、库存一致性、Kafka LAG。
- 完成标志：单机峰值达到约 1 万 QPS，且不超卖、账目自洽；如果仍不到 1 万，必须用数据说清楚下一处瓶颈在哪。
- 风险：中。改的是核心扣减路径，必须重跑一致性校验；出问题可回退到标签 `phase6-docs-baseline`。
- **实测结果（已完成）**：
  - 峰值 **约 16,000 QPS**（256 VU 时 16,096），是 1 万目标的 1.6 倍；
    512 VU 时 14,855 QPS、p50 37.1ms / p95 56.7ms / p99 71.8ms（优化前同一档 p50 是 84.7ms）。
  - 逐档提升 **1.87× ~ 2.36×**，五档全部 0 错误、0 限流。
  - 一致性没有被牺牲：`sold` = 订单数 = 去重用户数 = 去重 `request_id` 数 = `SUM(quantity)`
    = **2,183,529**，Redis 剩余 **2,816,471** = 5,000,000 − 2,183,529；Kafka 6 个分区 LAG 全为 0。
  - 详细过程与 A/B 数据见 `docs/benchmark.md` 的「优化记录 8」。
- **下一处瓶颈（已用 CPU profile 定位）**：约 45% 的时间在阻塞式 socket 系统调用，
  其中 42% 是 `net.(*conn).Write`（把 HTTP 响应写回客户端），业务代码几乎不上榜。
  也就是说**代码侧已经到天花板**，再往上要靠部署层面：
  换 Linux（epoll）、`GOMAXPROCS` 调参、HTTP 长连接、单机多实例 + 负载均衡。
- **顺带产出的工具**：`cmd/server/pprof.go`——设 `ENABLE_PPROF=1` 启动才会在
  `127.0.0.1:6060` 开分析端口（默认关闭、只绑本机，不影响压测）。

#### 6.2 演示控制台（已完成）

- 目标：把「后端跑得怎么样」变成一眼能看懂的画面，面试时能现场演示。
- 定位：**不是电商前台**，只是一个演示用的控制台。商品列表、购物车、结算不做页面。
- 实际交付（新增 `internal/demo` 包，**只新增、没动后端业务逻辑**）：
  - `GET /demo`：单文件页面（`internal/demo/web/index.html`，用 `go:embed` 打进二进制，原生 JS，
    不需要 npm、不需要打包工具），深色主题，五个区块：一键准备 / 登录注册 / 独立秒杀页 / 实时观测 / 演示步骤。
  - `GET /demo/data`：只读接口。把 MySQL 的 `total_stock`、`sold`，Redis 的 `remaining_stock`，
    Kafka 的在途订单数 `pending` 拼成一份 JSON，页面每秒拉一次。
  - `POST /demo/seed`：一键造数据——商品 → SKU → 库存 → 秒杀活动（`now-5min` ~ `now+2h`）→
    秒杀商品 → 预热 Redis → 演示账号（`demo1..demoN`，密码 `demo1234`）。**幂等**：重复点不会造重复数据，
    只有秒杀活动每次新建。用 `DEMO_SEED=0` 启动即可关掉这个接口（返回 403）。
  - 配套改动（都是为了给演示页供数）：
    `seckill.Cache.Stock`（读 Redis 剩余，用 `redis.Nil` 区分「没预热」和「卖光了 0 件」）、
    `seckill.Queue.Pending`（在途订单数）、`seckill.Service.WarmUpStock`（把商品信息和库存一起预热）、
    `product.FindSKUByProductAndSpec`（造数据时判断 SKU 是否已存在）。
  - `internal/pkg/metrics/middleware.go` 新增 `ignoredPrefixes = ["/demo", "/metrics"]`：
    这两个前缀**不计入 `totalRequests`**，避免演示页每秒轮询污染压测口径。
    （秒杀成功/失败/重复/限流是业务层主动上报的，不走这里，不受影响。）
- 指标口径（页面上已按这个口径写死文案，讲的时候别说错）：
  `/metrics` 里的 `seckillRequests` 是**入口请求数**（每点一次抢购 +1）；
  而 `seckillSuccess / seckillDuplicate / seckillFailure` 是**消费者落库口径**（`internal/seckill/worker.go` 上报）。
  两者本来就会差几百毫秒到几秒，这个差值正好拿来演示「异步落库 + 在途订单」。
- 实测验证：
  - `gofmt -l cmd internal` 无输出；`go vet ./...` 无输出；`go build` 通过；
  - `GET /demo` → 200 / `text/html; charset=utf-8`；`POST /demo/seed` → 建出活动、商品和 3 个账号；
  - 抢购链路：首次 200；同 `request_id` 重放 → 409「重复的 request_id」；
    同用户换 `request_id` 再抢 → 409「超出每人购买限制」；换账号 → 200；
  - 一致性：造 50 件库存、抢 1 件，等 3~5 秒落库追平后 `sold=1`、Redis 剩余 `49`、`pending=0`；
  - 口径隔离：连打 5 次 `/demo` + 5 次 `/metrics` + 2 次 `/demo/data`，`totalRequests` 只涨了 2（那 2 次是 `/health`）；
  - `DEMO_SEED=0` 启动 → `POST /demo/seed` 返回 403，`GET /demo` 仍 200。
- 完成标志：打开页面点一下就能完成一次抢购，并且能同时看到压测指标在动。**已达成。**
- 风险：低。纯新增，不动后端业务逻辑。

#### 6.3 AI 辅助可观测（已完成）

- 目标：让系统自己发现异常，而不是靠人盯屏幕。
- 明确不做的事：**不做 LLM 导购 / 聊天推荐**。秒杀的设计目标就是把绝大多数流量挡在门外，
  再挂一个 AI 去「引导更多人买」在架构上是自相矛盾的，而且依赖外部 API，演示不可靠。
- 任务（按性价比排序，做多少算多少）：
  - 指标基线告警：给 QPS、错误率、Kafka LAG 建一条基线，持续偏离就告警（统计方法即可，不需要大模型）；
  - 压测结果自动总结：把压测输出和日志汇成一份报告，辅助定位瓶颈；
  - 自适应限流：按实时负载动态调整限流阈值，接在现有 `internal/pkg/ratelimit` 旁边。
- 完成标志：能演示「压测中系统自己报出异常并说明原因」。
- 风险：低到中。都属于旁路功能，不影响主链路。
- **实测结果（已完成）**：
  - 新增代码：`internal/pkg/metrics`（`metrics.go` 补齐错误数/平均延迟/并发数，`window.go` 采样器，
    `alert.go` 告警引擎，`rules.go` 四条默认规则，`http.go` 两条只读接口）、
    `internal/pkg/kafka/lag.go`（消费组积压探针）、`internal/pkg/ratelimit/adaptive.go`（自适应限流）、
    `cmd/benchreport`（压测报告工具），并在 `cmd/server/main.go` 里接线、给演示页加了第 ⑤ 区块。
  - 告警实测：256 VU 压 20 秒，系统自己在 `15:40:05` 打出
    「突发流量：QPS 冲到 4705/s……越过门槛 500/s」，`15:40:27` 自动打出恢复事件（持续 22 秒、峰值 5257.7）；
    全程 5xx 峰值 0%、Kafka LAG 峰值 0、在途订单峰值 0。
  - 性能代价：`gofmt -l cmd internal` 无输出、`go vet ./...` 通过、`go build` 成功；
    同一条件 A/B 对比（256 VU / 20 秒）：加观测前 112,631 请求 / 平均 47.7ms / p99 60.0ms，
    加观测后 108,353 请求 / 平均 QPS 4,918 / p99 65.18ms —— **QPS 没有可见下降**
    （中间件每个请求多 3 次原子加法，纳秒级）。
  - 报告工具用法：
    `go run ./cmd/benchreport -k6 .tmp/k6_summary.json -log .tmp/srv_demo.log -out -`
    （`-out -` 只打印；不填 `-out` 会写到 `docs/reports/bench-<时间>.md`，样例见 `docs/reports/stage63-verify.md`）。
  - 已知限制：`/metrics/history` 一次可能返回几百 KB（900 个样本）；告警只活在本进程内存里，
    进程挂了就没人报，要外部告警得接 Prometheus + Alertmanager。

### 阶段 7：独立前台与演示内容

- 目标：给项目配一个**真的像电商的前台界面**，让「秒杀」有一个用户视角的入口，
  并提供一条可以现场演的双屏演示脚本。
- 定位（先说清不做什么）：做的是**「秒杀场景的最小可信前台」**，不是完整电商前台。
  购物车、结算、支付页面都不做——那部分已经有接口，缺的只是页面，对面试要讲的高并发没有增量。
  但**页面上的每一个数字都来自本项目真实接口**，没有一个是写死的假数据。
- 为什么另开 `/shop`，而不是把功能塞进已有的 `/demo`：
  这两个页面是**同一个后端的两个视角**，正好用来做双屏对比——
  - `/demo` 讲「系统内部此刻在干什么」：Redis 扣了多少、Kafka 压了多少、有没有告警；
  - `/shop` 讲「用户看到了什么」：有哪些商品、能不能抢、抢到没有、订单在哪。
  并排放在一起时，左边是用户的等待，右边是系统的运转，中间的因果关系就是讲解内容。

### 阶段 8：控制台压测命令生成器（已完成）

- 目标：把「跑压测」从「自己背命令、手改商品 ID」变成「点两下、复制、粘贴」，

- 本阶段最重要的决定是**不做什么**：不在服务端调用 k6。三条理由，面试时可以直接讲：
  1. 压测端和被压的服务跑在同一台机器上会互相抢 CPU，数字本身就不干净。

  3. 「生成命令」和「一键执行」的方便程度其实差不多（复制粘贴也就两秒），

### 阶段 9：订单超时关单与库存回补（已完成）

- 要解决的问题（一句话）：**抢到不付钱的人，会把库存永久占住。**
  阶段 8 结束时订单落库就停在「待付款」，再也没有下文——既不会超时、也不会取消。
  一个人用脚本把 1000 件库存全抢下来、然后一直不付款，商品就永远卖不出去了。
  这是电商里真实存在的攻击，叫「占库存」。真实系统一定有一段时间之后自动关单的机制。
- 本阶段的核心概念是**延时队列**。新手可以先这样理解：
  「我十分钟以后要处理这件事」——最直觉的写法是给每笔订单起一个定时器（`time.AfterFunc`）。
  这个写法在本项目里有三个致命问题：
  1. 定时器活在**进程内存**里。进程一重启，几万个定时器全部消失，那些订单永远不会被关掉；
  2. 几万笔订单就要几万个定时器对象，内存和调度都是负担；
  3. 多实例部署时，每个实例都在自己内存里管自己那份，没法统一。
  正确的做法是把「什么时候该处理」这件事**存到进程外面**。本项目用的是 Redis 的有序集合（ZSET）：

  ```
  ZADD seckill:orders:expire <到期时间戳> <request_id>
  ```

  - ZSET 的每个成员带一个分数（score），而 ZSET **按分数排序**。
    把分数当作「到期时间」，那么「所有已经到点的订单」就是
    「分数小于当前时间的那些成员」，一条命令就能捞出来：

    ```
    ZRANGEBYSCORE seckill:orders:expire -inf <当前时间戳> LIMIT 0 200
    ```

  - 用 `request_id` 当成员还顺手解决了去重：ZSET 的成员天然不重复，
    同一笔订单被写进去两次也只会有一条。
  - 时间戳用「Unix 秒」这种**绝对时间**，不是「几秒后」这种相对时间。
    相对时间必须有人记得去减，绝对时间写一次就完了，谁来读都一样。
- 光有延时队列不够，还需要一条**兜底**的路。因为延时队列存在 Redis 里，
  而 Redis 是有可能丢数据的（重启没落盘、内存淘汰、网络问题），
  更常见的是「订单刚写进 MySQL，进程就崩了，还没来得及写队列」——
  这笔订单的定时任务凭空消失，它会永远停在待付款。
  所以阶段 9 一共两条路，一条快、一条稳：

  | | 延时队列（正常路径） | MySQL 兜底扫描（安全网） |
  |---|---|---|
  | 数据来源 | Redis ZSET | `seckill_orders` 表 |
  | 触发方式 | 到点即处理 | 每 5 秒问一次「有没有早就该关的单」 |
  | 快慢 | 准点 | 慢一点，但一定会发现 |
  | 兜底对象 | —— | 队列漏掉、或 Redis 丢数据的那几笔 |

  这个「正常路径 + 兜底路径」的结构值得记住：**任何依赖外部组件的定时任务，
  都要有一份权威数据（这里是 MySQL）能被定期回查**，否则就是单点。
- 有两个地方的顺序和幂等必须写对，否则会算错账，面试官很爱问这两处：
  - **顺序：先改 MySQL，再改 Redis。** 反过来（先把库存加回 Redis）
    如果 MySQL 那边关单失败，库存就凭空多出一份——那是**超卖**，比少卖严重得多。
    先改 MySQL 的话，中途失败只是「Redis 暂时少了一份库存」，属于少卖，
    下一轮重试或者对账任务都能补回来。
    一句话总结：**朝安全的方向失败**。
  - **幂等要做两层，缺一不可。**
    - MySQL 那层靠条件更新：`UPDATE ... WHERE id = ? AND status = 'pending'`。
      只有把状态从「待付款」改成「已取消」**成功**的那一次调用（`RowsAffected = 1`）
      才算真的关单，重复调用第二次就已经没有 `pending` 的行可改了。
    - Redis 那层靠 `SETNX` 抢一个标记 key：`seckill:order:<request_id>:restored`。
      为什么 MySQL 那层不够？看这个场景：

      ```
      用户限购 3 件，第一单抢了 2 件，超时被关掉 → 库存 +2、该用户已买数回到 0
      用户马上又抢了 3 件               → 该用户已买数变成 3
      此时第一单的回补因为重试又执行一次  → 脚本看到「已买 3 >= 要还的 2」
      ```

      光看「已买数够不够扣」是拦不住的，库存会真的多出 2 件。
      所以必须有个只写一次的标记，**只有第一个执行到的调用者才真的回补**。
- 一个容易被忽略的语义问题：`seckill_items.sold` 到底代表什么？
  本阶段把它明确定义成「**还没有被取消的订单占用的库存**」——包含待付款的，不包含已取消的。
  为什么重要：对账任务是用「总库存 − sold」反推 Redis 剩余库存的。
  如果关单时只把 Redis 库存加回去、`sold` 不动，下一次对账会按「这一份还占着」重新算，
  刚还回去的库存又被吞掉。所以关单时必须**同时**把 `sold` 减回去。
- 还有一个必须先改掉的东西：`seckill_orders` 上原本有个 `idx_user_item` **唯一索引**
  （同一个用户同一个商品只允许一行）。加了超时关单之后它就成了绊脚石：
  用户超时被关单后想重新抢，插新行会直接撞唯一索引失败。
  处理办法是把它从唯一索引改成普通索引，「有没有买过」交给业务层按状态判断
  （`status IN ('pending', 'paid')` 才算买过），真正的守门员是 Redis 里按用户计数的那个 key。
  注意：`AutoMigrate` **不会**去改已经存在的同名索引（它发现名字在就直接跳过），
  所以新增了 `EnsureOrderIndexes`，启动时查一次 `information_schema`，是唯一索引就删掉重建。
- 压测数据带来的真实教训（这两个都是本项目真踩到的，不是假设）：
  - **① 兜底扫描必须有时间上限。** 库里躺着 440 万条压测遗留的待付款订单时，
    兜底扫描一上线就把它们全当成「超时」，每 5 秒啃 200 条要跑几十个小时，日志也被刷爆。
    定论：兜底扫描的职责是「延时队列漏掉的那几笔」，不是「修复停机几个月的历史数据」，
    后者属于运维脚本的活。所以加了 `expireSweepLookback = 6 小时`，更老的订单一律不动。
  - **② 扫描没索引就是一场事故。** 上面那个「只扫最近 6 小时」的条件，
    在没有索引时退化成**全表扫描**：6 小时窗口里一行都没有，MySQL 只能一行行扫完
    440 万行才敢说「没找到」，实测每次 **1.6 ~ 1.8 秒**，而扫描每 5 秒就有一轮——
    等于常年白烧一个 CPU 核去证明「啥也没有」。
    修法是加一条 `(status, created_at)` 复合索引，并把排序从 `ORDER BY id`
    改成 `ORDER BY created_at, id`：排序字段和索引顺序一致，MySQL 才能顺着索引
    取前 200 条就收工。改完执行计划从 `type: index`（扫全表）变成 `type: range`（`rows: 1`）。
- 有个细节容易漏：关单要分两步（先 MySQL 后 Redis），两步之间有个短暂的窗口，
  此刻 MySQL 的 `sold` 已经减了、Redis 库存还没加回来，两边正好差这一份。
  如果对账任务正好在这一瞬间跑，它会按 MySQL 反推、把 Redis 覆盖掉，把这笔账算错。
  处理办法是一个原子计数器 `inFlightExpiry`：关单前后 `+1 / -1`，
  对账任务每次先看一眼，非 0 就本轮跳过。它**不是锁**，只是给对账任务的一个信号。
- 怎么验证（新手也能照做，用环境变量把时限调短，不用真等 15 分钟）：
  1. 用短时限重启服务：`$env:SECKILL_PAY_TIMEOUT="30s"`（不设就是默认 15 分钟）；
  2. 去 `/shop/seckill?item=<商品ID>` 抢一件，页面显示「已抢到」和付款倒计时；

### 阶段 10：把限流从「固定窗口」换成「滑动窗口」（已完成）

- 要解决的问题（一句话）：**固定窗口在「整秒交界」的那一瞬间，会放过接近两倍的流量。**
  抢购接口限制的是「同一个用户 100 次/秒」。老实现是数数：
  `INCR ratelimit:seckill:user:<用户ID>:<窗口号>`，数到超过 100 就拒绝。
  这里的「窗口号」= `当前毫秒 / 1000`，意思是**把时间切成一个个「自然秒」**
  （第 1 秒是 0~999ms，第 2 秒是 1000~1999ms，以此类推）。
  问题就出在「自然秒」这个切法上。

- 先把这个洞讲清楚（面试也常问）。假设限制是 1 秒 100 次，看下面这条时间轴：

  ```
  第 1 秒                                    第 2 秒
  |--------------------------------|--------------------------------|
    ...  900ms      995ms   1000ms  1005ms        1090ms
          └── 打 100 次 ──┘        └── 再打 100 次 ──┘
  ```

  第一批 100 次落在**第 1 秒**这个窗口里 → 数到 100，没超，全放行。
  第二批 100 次落在**第 2 秒**这个窗口里 → 又是从一个空桶开始数，数到 100，也没超，全放行。
  可是从现实世界看：**这 190 毫秒内，系统实实在在放过了 200 次请求。**
  本来承诺的「1 秒最多 100 次」，在窗口交界处被放大了将近 2 倍。
  这类攻击有个名字叫「**边界突发**」：攻击者根本不用破解限流，只要掐着秒表，
  在整秒前后各打一发就够了。窗口分得越粗（比如按分钟切），这个洞就越大。

- 修法的核心思路只有一句话：**别数数，改成记时刻。**
  老实现记的是「这个窗口里来过几次」——它不知道具体是什么时候来的，
  所以窗口一翻页就全忘了。新实现把**每一次放行的时刻**原原本本记下来，
  判断依据就从「现在是第几个窗口」变成了
  **「最近 1000 毫秒内到底放行过几次」**——这正是「滑动窗口」这个名字的由来：
  窗口不是一个一个跳着走的，而是跟着当前时刻**连续地往前滑**。

- 怎么「记时刻」？用 Redis 的**有序集合（ZSET）**，本项目在阶段 9 的延时队列里已经用过它：

  ```
  ZADD ratelimit:seckill:user:15 1758364800123 "req-abc-123"
       └── key                    └── 分数     └── 成员
  ```

  ZSET 的每个成员带一个分数，而且**按分数排序**。这里把「放行时刻的毫秒时间戳」当分数，
  于是「谁已经滑出窗口了」就是一个范围查询，一条命令删掉：

  ```
  ZREMRANGEBYSCORE <key> 0 <当前毫秒 - 1000>   -- 删掉 1000 毫秒以前的记录
  ZCARD <key>                                  -- 数一数窗口里还剩几条
  ```

  `ZCARD` 的结果就是「最近 1 秒内放行过几次」。够 100 就拒绝，不够就放行并记一条。
  因为「删旧」和「数数」在同一个 Lua 脚本里执行，中间不会插进别的请求，
  所以这套判断是**原子**的——这一点很关键，否则并发下照样会算错。

- 有三个细节特别容易写错，而且都是真实踩过的坑：
  1. **只有「放行」的请求才记进 ZSET，被拒绝的不记。**
     直觉上好像该把被拒的也记上（"记录所有请求"），但那样窗口会被自己的拒绝记录越填越满：
     一旦被限流，后续每次请求都在往里塞记录，窗口永远腾不干净，
     变成「越限封得越久」，等于给用户加了一个越来越长的惩罚期。这是另一个 bug。
  2. **成员不能只用「毫秒时间戳」。** ZSET 的成员是**唯一**的，同一毫秒里来的两个请求
     如果用同一个时间戳当成员，后一个会把前一个**覆盖**掉——计数偏少，限流被放水。
     所以成员得是独一无二的东西：抢购热路径直接用 `request_id`（每个请求本来就有，
     而且同一个请求重放时不会多占一次配额，天然吻合幂等）；通用的那个限流器手上没有
     `request_id`，就用「毫秒时间戳 + 进程内自增序号」拼一个，保证同毫秒并发也不撞。
  3. **`PEXPIRE` 只是兜底，不是判断依据。** 判断完全靠 `ZREMRANGEBYSCORE` + `ZCARD`，
     过期只是防止 key 永远留在内存里。设成「最后一个放行时刻之后再过一整个窗口」
     就够长了（比如 1 秒的窗口就设 1 秒），到那时候 key 本来也空了。
     顺带一提：这条 `PEXPIRE` 和 `ZADD` 在同一段 Lua 里，是原子的，
     所以老实现那个「`INCR` 成功了但进程在 `EXPIRE` 之前挂掉，key 永远不过期」的隐患也一并消失了。

- key 的命名也跟着简化了。老 key 里带着窗口编号（`:1758364800`），因为要区分「这个窗口」
  和「下个窗口」；现在窗口是滑动的、不翻页，一个用户只需要一条 key：

  | | 老（固定窗口） | 新（滑动窗口） |
  |---|---|---|
  | key | `ratelimit:seckill:user:<用户ID>:<窗口号>` | `ratelimit:seckill:user:<用户ID>` |
  | 类型 | 整数（`INCR`） | 有序集合 ZSET |
  | 记的是什么 | 这个窗口里来过几次 | 每次放行的**时刻** |
  | 有效期 | 1 个窗口（1 秒） | 最后一次放行之后再 1 个窗口（1 秒） |
  | 判断 | `次数 > 100` | 最近 1 秒内的记录 `>= 100` |

- 这次一共改了两处限流，它们的取舍**故意不一样**，这点值得单独讲：
  - **抢购热路径**（`internal/seckill/cache.go` 的 `hotPathLuaScript`）：
    限流只是那段大脚本的**第 1 步**，后面接着读商品信息、校验活动时间、幂等判重、
    限购、预扣库存，全部共用**同一次 Redis 往返**。所以这里必须把滑动窗口的逻辑
    直接写进大脚本里，不能去调用别的限流器。
  - **秒杀管理接口**（建活动、建商品、查活动）用的是
    `internal/pkg/ratelimit/redis_limiter.go` 这个按 IP 的通用限流器，
    它本来就是独立的一次 Redis 往返，所以直接把它内部从固定窗口改成滑动窗口就行，
    `Limiter` 接口和 `middleware.go` 都不用动。
  - 那为什么不干脆让热路径复用这个通用限流器，少维护一份逻辑？
    因为**复用意味着多一次网络往返**（先问一次「能不能过」，再执行那段大脚本），
    正好把阶段 6.1「把入口 4 次 Redis 往返合并成 1 次」的优化还回去。
    宁可有两份长得像的代码，也不能牺牲热路径的往返次数——**热路径上每一次 RTT 都是要还的**。

- 怎么验证（关键是要能**看见**固定窗口那个边界洞，而不是只看代码）：
  1. 造两批请求，**同一个用户、每批 110 个**（每个请求的 `request_id` 各不相同），
     第一批卡在某个自然秒的 **500ms** 处发（离前后边界都很远），
     第二批卡在**下一个自然秒的 60ms** 处发。两批之间只隔几百毫秒。
  2. 用改动前的代码跑一遍：两批各放行约 100，**合计约 200**——
     几百毫秒内放过了 2 倍的量，这就是那个洞。
  3. 用改动后的代码跑一遍：第一批放满 100（后面 10 个被拒），
     第二批**全部被拒**（因为第一批的 100 条记录还在「最近 1000 毫秒」里），**合计约 100**。
  4. 本项目实测（把改动前的版本单独编译出来做 A/B 对照）：

     | 版本 | A 批放行 | B 批放行 | 合计放行 | 两批间隔 |
     | --- | --- | --- | --- | --- |
     | 固定窗口 | 100 | 100 | **200** | 305 毫秒 |
     | 固定窗口 | 100 | 100 | **200** | 282 毫秒 |
     | 固定窗口 | 94 | 100 | **194** | 213 毫秒 |
     | 滑动窗口 | 100 | 0 | **100** | 501 毫秒 |
     | 滑动窗口 | 100 | 0 | **100** | 371 毫秒 |

     结论：固定窗口在半秒内放过了接近 2 倍的量；滑动窗口稳定卡在 100，
     而且第一批正好放满、第二批全拒——正是预期中的形状。
  5. 顺手回归管理类接口的通用限流器：50 个并发请求**全部通过**（没有 429 误报），
     150 个并发请求**正好放行 100、拒绝 50**。
- 完成标志：抢购接口与秒杀管理接口的限流都是「最近 1 个窗口内」的滑动窗口，
  边界突发被消除，且没有误伤正常流量；`gofmt -l cmd internal` 无输出、
  `go vet ./...`、`go build ./...` 全部通过。**已达成。**
- 风险：低。改动局限在「限流这一小块」，不影响库存、订单、对账这些账目逻辑；
  热路径仍然是**一次 Redis 往返**，返回值约定（`-4` = 被限流）没有变。
  唯一的取舍是热路径与通用限流器各有一份滑动窗口实现（原因见上），
  以后要改限流算法得记得**两处都改**。

### 阶段 13：网关收口（已完成）

- 为什么做这一章：前 12 个阶段把功能和压测都做完了，但一直有一个问题没回答——
  「**万一将来要拆微服务，你从哪儿下手？**」。这一章的答案是：先把**网关**立起来。
  网关是微服务的第一块砖：它管「哪个路径归哪个服务」「谁需要登录」「这次请求的编号是什么」「请求转给谁」，
  这四件事想清楚了，后面把某个模块搬成独立进程就只是「换个上游地址」而已。
  完整的设计讨论（现状体检、三处硬耦合、目标形态、落地路线、代价对照）写在 `docs/microservices.md`。
- 这一章的关键词是「**旁路**」：网关是一个**新端口（默认 8081）**，
  它把请求转发给现在这个单体（默认 `http://127.0.0.1:8080`）。
  **`cmd/server/main.go` 一个字都不改**，秒杀热路径、压测脚本、演示页面全部照旧。
  这样做有三个好处：① 零回归风险，原来怎么压测还怎么压测；
  ② 出问题直接不启动网关就回退了；③ 可以拿「直连 8080」和「走 8081」做一次干净的性能对照。
- 这一章刻意不做的事：不动 `cmd/server`、不拆任何业务模块（真正的拆分是阶段 14 以后的事）、
  不引入服务发现和配置中心（服务数量是固定的，环境变量足够）。

  | 2 | `internal/user/auth.go` | `AuthMiddleware(trustHeader)` | 两段：①`trustHeader` 为真且 `X-User-Id` 有值 → 解析成数字放进上下文并放行（**解析失败要 401**），头里没值才往下走；②回退：`Authorization: Bearer <token>` → `jwt.Parse` → 放进上下文 | 带 token 走网关访问 `/me` → 200；不带 token → 401；伪造 `X-User-Id: abc` 直连 8082 → **401**（不是 200，也不是 500） |

- 为什么空 1 必须「默认关、而且只认白名单」：
  这个开关一旦打开，下游就**完全不检查令牌**了——请求头里写你是谁，你就是谁。
  所以默认值必须选最保守的（关）。而判断写成「只有 `1`/`true` 算开」、
  不能写成「只要不是 `0` 就算开」：后者遇到手滑写成 `flase` 会**静默打开**，没人会发现；
  前者最坏只是「以为开了其实没开」，一试就知道。
- 空 2 里最容易错的三点（注释里也写了，这里再点一遍）：
  1. **「解析失败」不等于「没有头」**。`X-User-Id` 里有值时，说明请求是「以网关的身份」进来的，
     格式不对就只能 401，**不能放它去走 JWT 那条路**——那等于给一个畸形请求第二条命。
  2. **不要在下游再删一次 `X-User-Id`**。网关已经做过「先删客户端伪造的、再写自己的结论」，
     下游再删一次就把自己要读的值删掉了，信任头模式直接失效。
  3. **失败一律用 `c.AbortWithStatusJSON`**，不要用 `c.JSON`。用后者的话，
     鉴权失败了后面的 handler 还会照常执行——等于没鉴权。

- 填空过程中实测抓出并修掉的 3 个缺陷（都很典型，建议记进面试素材）：
  1. **存进上下文的是 `uint64`，下游按 `uint` 取 → 取不到。**
     `strconv.ParseUint` 返回的是 `uint64`，而下游 `Me` 用 `v.(uint)`、`/shop/my` 用 `c.GetUint`，
     两者都是**严格类型断言**：存 `uint64` 时 `/me` 直接 401「登录状态无效」；
     而 `GetUint` 更危险——它**安静地返回 0**，接口会以「用户 0」的身份返回 200。
     对照实验：同一个 handler，8082 直连只带 JWT（存 `uint`）→ **200**；
     只带 `X-User-Id`（存 `uint64`）→ **401**。修法：`c.Set(contextUserID, uint(parsed))`。
  2. **第 1 段 `c.Next()` 后面漏了 `return`，响应体被拼成非法 JSON。**
     gin 里 `c.Next()` 执行完还会回到中间件继续往下走，于是又进了第 2 段。
     实测响应体变成 `{"error":"登录状态无效"}{"error":"无效的登录令牌"}`——两个 JSON 拼在一起。
     如果第 1 段的 handler 返回的是 200，第二个 JSON 会被**追加到 200 的响应体后面**
     （状态码已经发出去了，gin 只在日志里打一行 WARNING），前端 `JSON.parse` 直接失败。
     走网关时之所以没暴露，只是因为网关会把 `Authorization` 一起转发、第 2 段验签居然成功了——
     **是运气，不是正确性**。修法：`c.Next()` 之后加 `return`。
  3. **第 2 段少了 `Bearer ` 前缀检查。** `strings.TrimPrefix` 匹配不上时会原样返回整个字符串，
     于是 `Authorization: <裸令牌>` 也被接受（实测 200，而这里要求 401）。
     修法：先 `if !strings.HasPrefix(authHeader, "Bearer ") { 401 }`，再 `TrimPrefix`。
- 这三个缺陷有个共同点，值得记住：**它们都不会让程序崩，只会让「结果悄悄不对」**——
  多余的 JSON 被追加、用户 ID 变成 0、裸令牌被放行。所以每加一层鉴权/转发，都要用
  「正常 + 畸形 + 缺字段」三类输入各打一遍，光看「服务还活着」是发现不了这类问题的。

- 为什么空 3 和空 4 是**同一件事的两半**：只关路由不关后台任务，单体就变成一具「不接客、
  却在后台偷偷改库存」的僵尸——外面看着 404 了，里面的对账循环照样每 30 秒跑一次。
  所以两者必须用同一个变量控制。（阶段 14 的 `USER_MODULE` 只涉及路由，因为它没有后台任务。）
- 为什么空 4 那半边**更要紧**：这三个任务都会改 Redis / MySQL 里的库存数字。
  如果一个进程刚把某件商品的库存扣掉，另一个进程又按 MySQL 里偏小的 `sold` 反推剩余库存、
  把刚扣掉的那部分**凭空加回去**——高并发下就是直接超卖。
  代码里确实有幂等保护（超时回补用 Redis SETNX 打标记、`cancelExpiredOrder` 可重复调用），
  但那些保护只挡得住「同一笔订单被重复处理」；挡不住「两个进程各自看到不同的世界」——
  因为 `Queue.Settled()`（对账用来判断「队列安静了吗」的那句）读的是**本进程内**的计数器
  （见 `internal/seckill/queue.go:173`），跨进程根本不成立。所以只能真的只让一个进程跑，不能指望幂等兜底。
- 为什么空 1 必须用 `runCtx`、不能抄单体的 `context.Background()`：
  单体是「进程一退，goroutine 自然就没了」，所以它怎么写都无所谓；
  而秒杀服务是从 `runCtx` 出发做优雅退出的——如果循环挂在 `Background()` 上，
  进程收到退出信号时它们**不会停**，下面那句 `defer stopRun()` 就形同虚设，进程会拖着不退出。
  这是本阶段唯一一处「抄的时候必须改」的地方，注释里也标了。
- 为什么 `seckillTrustHeader` 要**另起一个环境变量名**，而不是复用阶段 14 的 `TRUST_USER_ID_HEADER`：
  两个服务将来可能部署在不同机器上，各自需要一个开关；共用一个名字，
  总有一天会出现「只想改秒杀的，结果把用户服务的也改了」。
  另外它的**默认值必须是关**：信任头本身没有任何防伪能力，默认打开的话，
  任何人手写一个 `X-User-Id: 15` 就能免登录抢购、还能抢别人的限购名额。

- 填空过程中实测抓出并修掉的 4 个缺陷（都很典型，建议记进面试素材）：
  1. 用户写的 `}` 位置错，把后面的语句关进了错误的作用域（编译期就报错）。

  4. **（最值得记的一个）单体在 `SECKILL_MODULE=0` 时仍然创建了 6 个 Kafka 消费者。**
     原来创建消费者的循环放在开关**外面**，而 kafka-go 的 `NewReader` 一创建就加入消费组
     （`reader.go:744` 里有 `go r.run(cg)`）。结果：单体明明「让位」了，却仍有 6 个僵尸消费者
     占住 6 个分区里的 0/4/5，把消息**拉走却不处理**。现象极具迷惑性——抢购照样返回 **200**，
     但订单**永远不落库**，消费组积压涨到 **444 万条**。修法：把创建循环挪进
     `if os.Getenv("SECKILL_MODULE") != "0"` 里面，关掉时一个都不建；修复后消费组变成
     `Stable` 的 6 个成员、**0 个 `server.exe`**。教训：**「不注册路由」不等于「没在后台干活」**，
     凡是「一创建就有副作用」的组件（消费者、定时器）都要和路由纳入同一个开关。

    一度到 **713 万**，清理时一次扫出 20 万 + 68 万条 `user:*` key。这些 key 承担限购计数，

    「大于活动时长」的 TTL。
  - MySQL 里仍留着历史压测的 **~442 万条 pending 订单**，会拖慢 `ExpireLoop`
    （每 5 秒只处理 200 笔）。演示前建议先清空这些历史单，或调大 `expireBatchSize`。

### 阶段 16：拆 product-service（含 inventory），并拆掉下单里那条同库事务（已完成）

- 为什么做这一章：阶段 14、15 把 user 和 seckill 分别搬出去之后，`docs/microservices.md`
  第 3.1 节点名的那行「最贵的代码」还留在原地——`order.Place` 把「写订单」和「扣库存」
  放在**同一个 MySQL 事务**里。在单体里这是最省事、也最正确的写法，但它等于一根绳子
  把订单和库存拴在一起：**这两个模块永远没法分家**。这一章就是把绳子剪断。
- 关键词是「**搬家 + 剪绳子**」，拆成两件事：
  1. **搬家**：新增 `cmd/product`（默认 `:8084`），把 `internal/product` + `internal/inventory`
     一起搬过去；单体加一个 `PRODUCT_MODULE=0` 开关，一键让位（不设就是原来那个单体）。
  2. **剪绳子**：下单不再「本进程开一个事务同时写订单和扣库存」，改成
     **本地消息表（outbox）+ 跨进程同步扣减 + 后台重试补偿**。
- 名词先解释清楚（面试时如果不能把下面这三个词用大白话讲明白，这一章就白做了）：
  - **本地消息表 / outbox**：下单时先在**自己的库**里、和订单写在**同一个事务**里，
    额外写一张小纸条：「我欠库存服务一次扣减，编号是 xxx」。订单和纸条要么都写成功、
    要么都不写（本地事务管得住这个）。**这就是它比「直接调远程」可靠的地方**——
    不会出现「库存扣了、订单却没写成」这种找不回来的账。纸条落库之后，再拿着编号去调库存服务；
    调不动，就过一会儿拿纸条再来一次。
  - **幂等**：「同一个请求做两遍，结果和做一遍一样」。跨进程调用一定会超时重试，
    所以库存服务必须认得「这个编号我处理过了」——否则重试就会把库存扣两遍，也就是超卖。
  - **最终一致**：中间那一小段时间（订单是 `pending_stock`、库存还没扣）两边的数字对不上，
    这是**设计好的正常状态**，不是 bug；靠后台重试慢慢收敛。
- 这一章刻意不做的事：
  - **不把 inventory 再拆成独立进程**。商品和库存是同一条业务链（看 SKU 就要看库存），
    拆开只会多一跳、多一个故障点，换不来任何好处。
  - **不为这件事引入 MQ**。这里要的是「当场知道成功还是失败」，Kafka 是异步单向的，
    用它反而要再绕一套回执。秒杀用 Kafka 是因为一万 QPS 的写请求必须削峰，普通下单没有这个量级。
  - **不上分布式事务（2PC / Seata）**。整个系统就两个进程，用「本地消息表 + 重试」这种
    最土也最稳的做法足够，而且每一行代码都能讲清为什么这么写。
  - **不删单体里的商品 / 库存代码**。不设 `PRODUCT_MODULE` 就是老样子，退路永远留着。

- **库存服务这边的关键设计**：`internal/inventory/deduct.go` 的 `ApplyDeduct`。
  它是整章正确性的地基，四步都值得记住：

  | 步 | 做什么 | 为什么 |
  | --- | --- | --- |
  | 1 | 先按 `request_id` 查账本 `stock_deducts` | 查到了就直接回上次的结论——重试绝不能把库存扣两遍 |
  | 2 | 查不到 → 在**一个事务**里「先占坑、再扣减」（占坑 = 插一行 `request_id` 唯一的记录） | 占坑和扣减同生共死：进程万一崩在中间，占坑跟着回滚，不会留下「账本说扣过、库存其实没动」的假账 |
  | 3 | 扣减按 SKU ID **排序**后逐个 `UPDATE ... WHERE quantity >= ?` | 两笔单都要扣 SKU 3 和 7，一笔按 3→7、一笔按 7→3，并发起来就会互相等对方的行锁（死锁）；固定顺序是最省事的解法 |
  | 4 | 库存不足时把 `rejected` 也记进账本 | 这个编号以后每次重放都得到同一个答案，不会出现「先说不成功、后说成功」的反复 |

  「占坑插不进去」还有另一种情况：**另一个请求正在处理同一个 `request_id`**。
  这时不能瞎猜结果，返回 `ErrDeductInProgress`（HTTP 409 + `code=deduct_in_progress`），
  意思是「现在还不知道结果，晚点再问」。
- **订单状态机多了一个中间态 `pending_stock`**（`internal/order/model.go`）：

  | 状态 | 含义 | 用户看到什么 |
  | --- | --- | --- |
  | `pending_stock` | 订单已收下，库存还在确认（阶段 16 新增） | 「订单已收下，正在确认库存」+ 刷新状态按钮 |
  | `pending` | 库存已扣成功，等付款 | 正常的待付款 + 付款倒计时 |
  | `cancelled` | 已取消（用户取消 / 库存不足 / 重试超限） | 已取消 |
  | `paid` | 已付款 | 已支付 |

  `pending_stock` 也算「占住了一单」，但付款接口**不允许**它付款：
  库存都还没确认就让用户付钱，等于卖一件可能不存在的货。
- **后台补偿任务** `RetryLoop`（`internal/order/retry.go`，每 2 秒一轮，挂在 `runCtx` 上）：
  1. 捞出「便签还是 pending、到了重试时间、次数没用完」的订单（`RetryBatchSize=20`）；
  2. 逐条**领取**（`ClaimOutboxRetry`，行锁 + 30 秒租约），领不到说明别的实例在处理，跳过；
  3. 复查订单状态（这中间用户可能已经取消了，取消掉的单子不能再扣库存）；
  4. 调库存服务：成功 → 订单 `pending` + 便签 `done`；真的不够 → 关单 + 便签 `dead`；
     其它失败 → 次数 +1，按**指数退避**（1s → 2s → 4s …… 封顶 60s）约下一次。
  次数用光（`OutboxMaxAttempts=8`）就 `giveUp`：关单 + 便签判死 + 把原因留在 `last_error` 里。
  「放弃」不是「不管了」，而是把状态收拾干净，别让用户永远看到「确认中」。
- **一个容易搞混的顺序问题**：库存扣成功之后，是**先改订单状态、再划掉便签**。
  反过来的话，便签一划掉而订单状态没改成功，就再也没有人来救它了，订单会永远卡在 `pending_stock`。
  按现在的顺序，任何一步失败都还有重试兜着（重试会重新扣一次库存，幂等，不会多扣）。

  - `order_outbox` 里 `done` 的记录**不会自动清理**，长期跑会越积越多（本项目量级下无所谓，
    真上线要加「按时间清理」或者分区）。
  - 库存服务的内部接口**没有鉴权**，只靠「网关不认识 `/internal` 前缀」挡着（外网 404）。
    真上线要再加内网监听 / IP 白名单 / 内部 token。
  - 补偿任务目前按「单实例」设计。`ClaimOutboxRetry` 的行锁 + 30 秒租约已经能保证
    同一条便签不会被两个实例同时处理；但多实例下的批量扫描节奏还会重叠，量大了要再看。

### 阶段 17：拆 order-service（订单 + 购物车 + 支付）并给单体加 ORDER_MODULE 开关（已完成）

- 为什么做这一章：阶段 14~16 把 user、seckill、product 三个服务搬出去之后，
  `docs/microservices.md` 第 6 节路线表里还剩最后一格——订单。这一章把
  **订单（`internal/order`）+ 购物车（`internal/cart`）+ 支付（`internal/payment`）**
  一起搬成 `cmd/order`（默认 `:8085`），单体加一个 `ORDER_MODULE=0` 开关一键让位。
- 为什么三块一起搬，而不是拆成三个服务（面试可以直接讲）：
  - `payments` 表存的是「哪张订单付过款」，离开订单表就没有意义；购物车记录的是
    「这个用户准备买什么」，和订单共享同一个用户边界、同一段购买流程。
  - 三块同库同进程，支付可以直接调用订单服务（进程内函数调用），**一次付款不产生
    跨服务网络往返**。硬拆成三个服务，就要跨两次网络，每一跳都可能超时、重试、乱序，
    换来的不是解耦，而是更多要自己兜底的失败场景。
  - 一句话：**微服务的边界按「数据归属 + 一致性要求」划，不是越细越好。**
- 这一章刻意不做的事：
  - **不动 `/shop` 和 `/demo`**。`internal/shop` 只依赖 product + seckill，
    `internal/demo` 直接拿四个模块的 Service 对象（进程内函数调用，不是 HTTP）。
    它们要真正独立，得先改成调接口，工作量比搬三块代码大得多，留给阶段 18。
  - **不引入新的 MQ 或分布式事务**。三块同库同进程，支付对订单是进程内调用；
    当前「改订单状态 + 写支付流水」仍是先后两次更新，靠 `Pay` 幂等 + 回调重试收敛，
    真要收成一个数据库事务还得再包一层，本阶段不做。
  - **不删单体里的三块代码**。不设 `ORDER_MODULE` 就是老样子，退路永远留着。

- 具体动了什么（三处）：

  | 文件 | 改动 | 说明 |
  | --- | --- | --- |
  | `cmd/order/main.go`（新增） | 新进程入口 | 装配 order / cart / payment 三个模块；`AutoMigrate` 六张表；`/healthz` + `/health`；全部路由挂鉴权；启动库存补偿 `RetryLoop` |
  | `cmd/server/main.go` | 加 `ORDER_MODULE` 开关 | 设 `0` 时**不注册** `/orders`、`/cart`、`/payments` 三组路由，也**不启动** `RetryLoop`；不设就是原来的单体 |
  | `Makefile` | 加 `run-order` / `build-order` | 和 `run-product` 同一套写法 |

- 服务边界（这一章结束后）：

  | 进程 | 端口 | 管什么 | 独占的数据表 |
  | --- | --- | --- | --- |
  | `cmd/server`（单体兜底） | `:8080` | `/shop`、`/demo`、以及还没搬走的接口 | 不独占（`/demo` 会跨模块读写） |
  | `cmd/gateway` | `:8081` | 统一入口、鉴权、注入 `X-User-Id` | 无 |
  | `cmd/user` | `:8082` | `/login`、`/register`、`/me` | `users` |
  | `cmd/seckill` | `:8083` | `/seckill/**`、`/metrics` | `seckill_activities`、`seckill_items`、`seckill_orders` |
  | `cmd/product` | `:8084` | `/products`、`/stocks`、`/internal/stocks/deduct` | `products`、`skus`、`stocks`、`stock_deducts` |
  | `cmd/order` | `:8085` | `/orders/**`、`/cart/**`、`/payments/**` | `orders`、`order_items`、`order_outbox`、`carts`、`cart_items`、`payments` |

- 环境变量（只列这一章新增 / 相关的）：

  | 变量 | 给谁用 | 默认 | 作用 |

  | `PRODUCT_SERVICE_URL` | `cmd/order` | `http://127.0.0.1:8084` | 扣库存打到哪 |
  | `PRODUCT_SERVICE_TIMEOUT` | `cmd/order` | `3s` | 单次扣减超时 |
  | `ORDER_MODULE` | `cmd/server` | 不设（= 开） | 设 `0` 时单体让出订单 / 购物车 / 支付三组路由与补偿任务 |

- 验收点：
  1. 8080 上 `/orders`、`/cart/items`、`/payments/1` → **404**；8085 上同样路径 → **200 / 401**（确认真的搬走了）；
  2. 订单服务**不带** `X-User-Id` → **401**（鉴权没有被搬丢）；
  3. 经网关 `:8081` 用登录 token 下单成功，响应里的 `user_id` 等于 token 的主人（证明网关 → 订单服务 → `X-User-Id` 这条链路是通的）；
  4. **并发下单不超卖**：库存 N 的 SKU 同时来 M 笔单，成功笔数**恰好**等于 N；
  5. 支付走订单服务：`pending` → `paid`，状态与 `payments` 表一致；
  6. `X-Trace-Id` 在网关、订单服务、商品服务三段日志里是**同一个值**；
  7. 不设 `ORDER_MODULE` 时单体照旧能跑（回退路径有效）。

- 实测记录（2026-10-15 直连验证 + 2026-10-20 网关验证）：
  - 三件套：`gofmt -l cmd internal` 无输出、`go vet ./...`、`go build ./...` 干净。
  - 拆分生效：8080 的 `/orders`、`/cart/items`、`/payments/1` 全是 **404**；
    8085 不带用户头 → **401 `无效的登录令牌`**；带 `X-User-Id: 15` 加购物车、查购物车都是 **200**。
  - **并发不超卖（核心指标）**：SKU 3 库存 **8**，20 个并发请求各买 1 件 →
    **200 恰好 8 个 / 409 恰好 12 个 / 其它 0 个**。MySQL 复核：`stocks.quantity = 0`；
    这 20 个 `request_id` 在 `orders` 里**只有 8 行**（7 `pending` + 1 `paid`）；
    `order_outbox` 8 条全部 `done`；库存不足的 11 笔订单 + 明细 + 便签**一行都没留**
    （`DeleteOrderCascade` 真的撤干净了）。
  - 支付：对其中一张订单 `POST /orders/57/pay` → **200 `支付成功`**，
    再查订单状态 `pending` → **`paid`**。
  - **重复支付回调（本轮补验）**：同一张订单连续回调两次 → **两次都是 200**，
    `payments` 仍然只有一条 `paid` 流水；再模拟「订单已改成 `paid`、流水还停在
    `pending`」的崩溃窗口，回调一次就能把流水补成 `paid`（靠 `Pay` 对已付款订单返回成功）。
  - **经网关**：`GET :8081/healthz` → 200；不带 token 的 `POST :8081/orders` → **401**；
    登录后 `GET :8081/cart/items` → 200（2 件）；`POST :8081/orders` → 200（订单 id 78，`user_id=15`）；
    网关日志显示 `order → http://127.0.0.1:8085`，说明一个环境变量就把流量挪走了。
  - **trace 跨三进程**：拿一个必然 409 的请求（SKU 3 已售罄）带 `X-Trace-Id: stage17-gw-trace2`，
    网关、订单服务、商品服务三份日志都出现**同一个** id。
  - **回归**：`/health`、`/shop`、`/shop/seckill`、`/shop/cart`、`/shop/data`、`/demo`、`/demo/data`
    全 **200**；秒杀端到端照常（`demo2` 抢 item 52 → `queued`，3 秒后 `seckill_orders` 出现
    `pending`，`sold` 0 → 1）。
  - **并发下观察到的一个坑（已修）**：20 并发那一轮，日志里出现过一句
    「补偿判定库存不足，已关单 order=62」，但库里根本没有 62。原因是便签的
    `next_retry_at` 初始化成了「现在」，后台 `RetryLoop` 在同步扣减还没返回时就抢到了同一张便签；
    两条路径都判「库存不足」，最终状态没错，但日志会骗人。更坏的交错是
    「同步路径撤单、后台路径却把订单改成 pending」——客户端收到 409，库里却留了一张待付款订单。
    修复很小：把首次可重试时间推后 `2 × RetryInterval`（默认 4s，大于 3s 的扣减超时），
    后台就只接手「同步路径已经放弃 / 进程崩了」的便签（见 `internal/order/service.go` 的注释）。

- 遗留 / 不足（记下来，暂不改）：
  - `/shop`、`/demo` 还在单体里，而且 `/demo` 是**直接调用各模块的 Service 对象**（进程内函数调用），
    不是走 HTTP。它们要独立成 shop-service / console-service，得先把这些调用改成接口，
    这是阶段 18 的主要工作。
  - 单体与订单服务启动时都会 `AutoMigrate` 同样的六张表。GORM 的迁移是幂等的，不会改坏数据，
    但「两个进程都能改表结构」本身不是好习惯；真上线应该把迁移交给单独的 job。
  - `TRUST_USER_ID_HEADER` 是「信任网关」的开关，只能在内网监听；如果 8085 暴露到公网，
    任何人手写一个 `X-User-Id` 就能冒充登录。
  - 订单服务的内部扣库存接口同样没有额外鉴权，靠「网关不认识 `/internal` 前缀」挡着。

## 阶段 18：拆出 shop-service 与 console-service（已完成）

### 18.1 这一阶段要解决什么

阶段 17 结束时，业务后端已经拆成了 user / seckill / product / order 四个服务，
但还有两块「组装型」代码留在单体里：

- `internal/shop`：给普通用户看的商城列表、秒杀独立页、购物车页；
- `internal/demo`：给面试官看的演示控制台，以及「一键造数据」。

它们和业务模块的区别是：**自己一张表都不管**。
`shop` 只是把商品、秒杀数据拼成页面要的 JSON；`demo` 只是替人把商品、库存、活动、账号建出来。
这类代码最适合单独跑，因为它们可以随意重启、扩容，出了故障也不影响下单和抢购。

这一阶段把它们拆成两个进程：

| 进程 | 默认端口 | 负责什么 | 自己拥有数据表吗 |
| --- | --- | --- | --- |
| `cmd/shop` | `:8086` | `/shop`、`/shop/seckill`、`/shop/cart`、`/shop/data`、`/shop/my` | 否 |
| `cmd/console` | `:8087` | `/demo`、`/demo/data`、`/demo/seed` | 否 |

### 18.2 为什么叫「纯组装服务」

直白地说：它们像餐厅前台，不负责种菜、不做菜，只把客人要的信息从后厨几个窗口取回来拼成一份菜单。

- 单体模式：前台和厨师在同一个房间，喊一嗓子就能拿到数据（进程内函数调用）；
- 独立模式：前台搬到了另一个房间，只能打电话问后厨（HTTP 请求）。

代码里对应两种适配器：

| 适配器 | 什么时候用 | 怎么拿数据 |
| --- | --- | --- |
| `local_adapters.go` | 单体启动 | 直接调用 `product.Service`、`seckill.Service` 等对象 |
| `http_client.go` | 独立进程启动 | 调用兄弟服务的 `/internal/...` 接口 |

页面组装代码（`Handler`）只认接口，不认背后的实现。
这样「单体」和「微服务」共用同一份页面逻辑，不会出现两套页面各改各的。

### 18.3 单体怎么保留回退能力

和阶段 14～17 一样，单体必须还能单独跑。新增两个开关：

| 变量 | 给谁用 | 默认 | 作用 |
| --- | --- | --- | --- |
| `SHOP_MODULE` | `cmd/server` | 不设（= 开） | 设 `0` 时单体不注册 `/shop` 路由 |
| `CONSOLE_MODULE` | `cmd/server` | 不设（= 开） | 设 `0` 时单体不注册 `/demo` 路由 |

不设这两个变量时，阶段 17 的行为完全不变；
都设成 `0` 时，两块页面分别由 `:8086` 和 `:8087` 提供，单体只保留真正搬不走的接口。

### 18.4 内部接口契约

独立模式的 shop / console 不直接连 MySQL、Redis、Kafka，只能通过下面这些内部接口取数或造数。
这些接口都注册在 `/internal` 前缀下，网关的路由表不认识这个前缀，所以从外网经网关访问会得到 404。

#### 商品服务（`:8084`）

| 方法 | 路径 | 用途 | 返回 |
| --- | --- | --- | --- |
| `GET` | `/internal/products/skus?product_ids=1,2,3` | 一次拿多个商品的规格 | `{"skus":[...]}` |
| `POST` | `/internal/products/skus/find` | 按「商品 + 规格」查 SKU | `{"sku":{...}}` 或 `{"sku":null}` |

控制台还需要「列商品、建商品、建 SKU」，直接复用已有的公开接口
`GET /products`、`POST /products`、`POST /products/:id/skus`。

#### 秒杀服务（`:8083`）

| 方法 | 路径 | 用途 | 返回 |
| --- | --- | --- | --- |
| `GET` | `/internal/seckill/activities` | 列活动 | `{"activities":[...]}` |
| `POST` | `/internal/seckill/activities` | 建活动 | `{"activity":{...}}` |
| `GET` | `/internal/seckill/activities/:id/items` | 列某场活动的秒杀商品 | `{"items":[...]}` |
| `POST` | `/internal/seckill/activities/:id/items` | 往活动里加秒杀商品 | `{"item":{...}}` |
| `GET` | `/internal/seckill/items/:id/stock` | 读 Redis 剩余库存 | `{"remaining_stock":10,"stock_ready":true}` |
| `POST` | `/internal/seckill/items/:id/warmup` | 预热 Redis | `{"status":"ok"}` |
| `GET` | `/internal/seckill/pending` | 读 Kafka 在途订单数 | `{"pending":0}` |
| `GET` | `/internal/seckill/users/:uid/orders` | 查某个用户的秒杀订单 | `{"orders":[...]}` |
| `GET` | `/internal/seckill/config` | 读付款时限 | `{"pay_timeout_seconds":900}` |

#### 用户服务（`:8082`）

控制台造演示账号直接复用公开接口 `POST /register`。
用户已存在时它返回 `409`，控制台把 `409` 翻译成 `user.ErrUsernameTaken`，当成「上次已经建好」跳过。

4. 经网关 `:8081` 访问 `/shop`、`/shop/data`、`/demo`、`/demo/data` 都是 200；

### 18.8 已知风险

- **页面里的请求是相对路径**。例如页面会去调 `/login`、`/cart/items`、`/shop/data`。
  经网关打开页面时一切正常；直接打开 `http://127.0.0.1:8086/shop` 虽然能看到页面，
  但页面里的业务请求会打到 shop 自己，可能得到 404。
  这是「页面服务只负责发页面」的必然结果，不能靠给 shop / console 加全量反向代理掩盖。
- **shop / console 不拥有数据**。它们一旦连不上下游，页面会报错，但不会破坏业务数据。
- **内部接口没有额外鉴权**。当前只靠「网关不认识 `/internal` 前缀」隔离；
  真上线必须改成只监听内网、加 IP 白名单或服务间认证。
- **HTTP 客户端超时是必须的**。不设超时，一个下游卡住就会把页面请求一直挂住。

### 18.9 HTTP 客户端的正确实现

两个独立服务各有一个通用的 `do(...)`，它只做一件事：替页面服务给兄弟服务打电话。
这里最容易犯的不是「不会发请求」，而是把请求和响应接反：

- 请求体必须作为 `http.Request.Body` 发给下游。只把 JSON 写进一个名叫 `body` 的请求头，
  下游仍然会收到一个空请求体，`POST /register`、`POST /seckill/activities` 会直接返回 400；
- 响应必须从 `resp.Body` 读出来再解析。拿请求序列化后的字节去 `json.Unmarshal`，
  GET 时它通常是空切片，结果就是 `unexpected end of JSON input`；
- 拿到 `resp` 后必须 `defer resp.Body.Close()`。即使内容已经读完，也要归还连接资源；
- 响应最多读 64KB，防止一个失控的下游用超大响应把本服务内存吃掉。

最终两份实现统一按这个顺序：

1. `body != nil` 时先 `json.Marshal`，再用 `bytes.NewReader` 作为请求体；
2. `http.NewRequestWithContext(ctx, method, url, reader)` 构造请求；
3. 有请求体时设置 `Content-Type: application/json`；
4. 把 `trace.FromContext(ctx)` 写进 `X-Trace-Id`；
5. `c.client.Do(req)`，然后 `defer resp.Body.Close()`；
6. 用 `io.LimitReader(resp.Body, 64<<10)` 读取响应；
7. 非 2xx 保留状态码和响应体。`shop` 返回可读错误，`console` 返回 `statusError`，
   后者让 409「用户名已存在」可以翻译成正常业务结果；
8. 2xx 且 `out != nil` 时，把**响应字节**解析到 `out`。

两个包各补了单元测试，覆盖 POST 请求体确实到达下游、Content-Type、trace 透传、
正常 JSON 解析、非 2xx 状态保留，以及响应体关闭。

## 8. 挖空式协作规则

- 编码代理搭好骨架，留出关键函数或逻辑的“空”，让用户动手填写。
- 用注释提示思路，例如 `// TODO(你来实现)：这一步要做……`。
- 除非用户明确直接命令“帮我把这个模块完成”，否则不自行把模块写完。
- 用户写完后，代理帮助检查、解释、指出问题，但以用户完成为主。

## 10. 验收标准

- 目标 QPS：约 1 万。
- 核心接口 P99 延迟尽量低，错误率可控。
- 秒杀结束后库存恰好为 0，不超卖。
- 同一用户不能重复抢购成功。
- Redis 与 MySQL 最终一致，具备补偿/对账能力。
- Kafka 不出现不可恢复的消息丢失或重复处理导致的数据错误。
