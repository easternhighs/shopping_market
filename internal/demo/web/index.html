① 一键准备演示数据

会自动准备好：商品 → SKU → 库存 → 秒杀活动 → 秒杀商品 → 演示账号， 并把库存预热进 Redis。反复点也安全，商品和账号会复用，只有活动是新的一场。

抢购接口是需要登录的。演示账号由上面「一键准备」创建：用户名 demo1、demo2…， 密码统一是 demo1234。

⚠ 「Redis 剩余」才是抢购真正的闸门：能不能抢到，是 Redis 里的 Lua 脚本一锤定音的。 「MySQL 已售」是最终账本，比 Redis 慢一拍——两者相差多少，就是此刻还在 Kafka 里排队的订单数。

④ 实时观测

数字来自 /metrics，由服务自己上报，每秒刷新一次。用 k6 压测时，这些数字会飞起来。 本页面自己的轮询请求不计入「业务总请求」（服务端对 /demo、/metrics 做了排除）， 所以这个数字始终只代表真实业务流量。
注意「秒杀请求」和「落库成功」是两套口径：前者是入口收到多少次请求，后者是消费端真的往 MySQL 写成功多少单。 中间隔着 Kafka，所以落库口径会慢一拍——压测刚停下来时两者对不上是正常的，等几秒就追平了。

⑤ 系统自己报异常（AI 辅助可观测）

这一块不是让 AI 推荐商品，而是让系统自己发现问题：给 QPS、5xx 错误率、Kafka 积压各建一条「平时是多少」的基线， 连续几个采样窗口明显偏离就报警，并用一句人话说清发生了什么、该去看哪里。 判断用的是统计方法（基线均值 ± N 倍波动 + 绝对下限），不依赖任何外部大模型，断网也能跑。
门槛 = 「基线 + N 倍波动」和「绝对下限」里更严的那个。注意：秒杀时 QPS 冲到几千是预期行为（ 有下限兜着才不会一有流量就报），真正要紧的是错误率和积压——这两个涨起来才说明系统扛不住了。

⑥ 压测命令生成器（压测交给 k6）

压测故意不在服务端执行，理由有三条：
① k6 和被测服务跑在同一台机器上会互相抢 CPU，压测端自己先成瓶颈。这一点 docs/benchmark.md 里有实测：同时开两个 k6 进程打同一个服务， 总吞吐反而从 16,000/s 掉到 13,000/s；
② 让一个 Web 接口去启动外部进程，本质上就是一条「远程命令执行」的风险面，演示项目没必要背这个锅；
③ 命令行的参数很容易记错（尤其是 NS 这一项），与其写死一句让人每次手改商品 ID，不如把参数做成表单。
所以这一块只干一件事：把参数拼成一条能直接粘贴运行的完整命令。复制走，去另一个终端跑，本页负责看指标。

常用档位

档位怎么选（本机 20 核实测，见 docs/benchmark.md「A/B 实测」那张表）： 64 VU ≈ 10,400 QPS；256 VU ≈ 16,100 QPS 是峰值档；512 VU 之后反而回落， 因为瓶颈已经从代码转移到了单机网络栈。「1 万 QPS」这个目标，64 VU 就已经越过了。
两个必须知道的点：VUS 是并发虚拟用户数、不等于 QPS； 脚本固定往 http://127.0.0.1:8080 发压，所以 k6 要和本服务在同一台机器上跑。

⑦ 现场怎么演示

    

      0）先点右上角「打开前台商城」：那是给用户看的独立前台（/shop），
      本页是给面试官看的仪表盘。两个页面看的是同一套后端，只是一个讲「用户看到了什么」，
      一个讲「系统内部在干什么」——双屏演示就是这么来的（详见 docs/interview.md）；

      1）点「一键准备」，页面立刻有库存进度条和倒计时；

      2）用 demo1 登录后点「立即抢购」——第一次成功，第二次会返回 409「您已经抢购过该商品」（这就是防重复购买）；

      3）换个账号 demo2 再抢，库存数字同步往下掉；

      4）跑到第 ⑥ 块点「复制命令」，在另一个终端（项目根目录）粘贴执行——商品 ID 已经帮你填好了；
      一边看「秒杀请求」往上冲、一边看 Redis 剩余掉到 0，同时「Kafka 在途订单」短暂变大后回落到 0（说明异步落库追平了）；

      5）压测跑到十几秒时看第 ⑤ 块：会出现「突发流量：QPS 冲到 xxxx/s，平时约 0/s，越过门槛 500/s」这样的告警，
      压测停几秒后同一条规则会自动恢复——这就是「系统自己发现异常并说明原因」。
