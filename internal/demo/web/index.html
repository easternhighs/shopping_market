① 一键准备演示数据

会自动准备好：商品 → SKU → 库存 → 秒杀活动 → 秒杀商品 → 演示账号， 并把库存预热进 Redis。反复点也安全，商品和账号会复用，只有活动是新的一场。

② 登录（拿 JWT）

抢购接口是需要登录的。演示账号由上面「一键准备」创建：用户名 demo1、demo2…， 密码统一是 demo1234。

⚠ 「Redis 剩余」才是抢购真正的闸门：能不能抢到，是 Redis 里的 Lua 脚本一锤定音的。 「MySQL 已售」是最终账本，比 Redis 慢一拍——两者相差多少，就是此刻还在 Kafka 里排队的订单数。

④ 实时观测

数字来自 /metrics，由服务自己上报，每秒刷新一次。用 k6 压测时，这些数字会飞起来。 本页面自己的轮询请求不计入「业务总请求」（服务端对 /demo、/metrics 做了排除）， 所以这个数字始终只代表真实业务流量。
注意「秒杀请求」和「落库成功」是两套口径：前者是入口收到多少次请求，后者是消费端真的往 MySQL 写成功多少单。 中间隔着 Kafka，所以落库口径会慢一拍——压测刚停下来时两者对不上是正常的，等几秒就追平了。

⑤ 系统自己报异常（AI 辅助可观测）

这一块不是让 AI 推荐商品，而是让系统自己发现问题：给 QPS、5xx 错误率、Kafka 积压各建一条「平时是多少」的基线， 连续几个采样窗口明显偏离就报警，并用一句人话说清发生了什么、该去看哪里。 判断用的是统计方法（基线均值 ± N 倍波动 + 绝对下限），不依赖任何外部大模型，断网也能跑。
门槛 = 「基线 + N 倍波动」和「绝对下限」里更严的那个。注意：秒杀时 QPS 冲到几千是预期行为（ 有下限兜着才不会一有流量就报），真正要紧的是错误率和积压——这两个涨起来才说明系统扛不住了。

⑥ 现场怎么演示

1）点「一键准备」，页面立刻有库存进度条和倒计时；
2）用 demo1 登录后点「立即抢购」——第一次成功，第二次会返回 409「您已经抢购过该商品」（这就是防重复购买）；
3）换个账号 demo2 再抢，库存数字同步往下掉；
4）跑压测：k6 run -e MODE=seckill -e VUS=256 -e HOLD=10s -e ITEM=<上面的商品 ID> k6_bench.js， 一边看「秒杀请求」往上冲、一边看 Redis 剩余掉到 0，同时「Kafka 在途订单」短暂变大后回落到 0（说明异步落库追平了）；
5）压测跑到十几秒时看第 ⑤ 块：会出现「突发流量：QPS 冲到 xxxx/s，平时约 0/s，越过门槛 500/s」这样的告警， 压测停几秒后同一条规则会自动恢复——这就是「系统自己发现异常并说明原因」。
